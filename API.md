# QZPAY API — проект v0.1

**API ещё не реализован. URL и ключи не выданы.** Текущий сайт — демо с данными браузера.

## Процесс и расчёт
Бот №1 создаёт заявку при запросе реквизитов. Сервер выбирает включённые реквизиты, фиксирует курс и резервирует депозит оператора. Бот передаёт чек, оператор принимает решение на сайте.

`net_usdt = amount_kzt × 0.90 ÷ rate`. 20000 ₸ при 485 = **37.113402 USDT**. Предлагаемая точность — 6 знаков, округление half-up; отображение — 2 знака. Комиссия 2000 ₸ учитывается отдельно. Суммы API — десятичные строки, серверная арифметика — точная.

Создание резервирует USDT. Подтверждение уменьшает депозит и увеличивает задолженность заказчику. Через 25 минут резерв освобождается. Позднее подтверждение повторно проверяет доступные средства. Выплата уменьшает задолженность без повторного списания депозита.

## Предлагаемые методы
| Метод | Назначение |
|---|---|
| POST /api/v1/orders | Создать заявку и получить реквизиты |
| GET /api/v1/orders/{id} | Получить статус и расчёт |
| POST /api/v1/orders/{id}/cancel | Отменить ожидающую заявку |
| POST /api/v1/orders/{id}/receipt | Прикрепить чек |
| GET /api/v1/balance | Депозит, доступная сумма, резерв, задолженность |
| POST /api/v1/withdrawals | Запросить ручной вывод |
| GET /api/v1/withdrawals/{id} | Статус вывода и хеш транзакции |

## Авторизация
`Authorization: Bearer <PARTNER_API_KEY>`. Ключ только на сервере бота. В БД хранится хеш. Для изменений требуется Idempotency-Key: повтор одинакового тела возвращает исходный результат, другое тело с тем же ключом — 409. Доступ ограничен объектами партнёра. Денежные изменения — в транзакциях общей БД с блокировками.

## Пример создания
```json
{"external_id":"order-001","amount_kzt":"20000","currency":"KZT","customer_reference":"client-123"}
```
Предлагаемые поля ответа: id, external_id, status, amount_kzt, rate, commission_percent, commission_kzt, net_usdt, expires_at, requisite (id, bank, recipient, account).

## Статусы
pending, confirmed, expired. Причины завершения без оплаты сохраняются отдельно: timeout, rejected, canceled. Позднее подтверждение допускает переход expired → confirmed. До запуска согласовать webhook с повторной доставкой или дополнительный опрос истёкших заявок: старый контракт бота №2 не покрывает этот сценарий.

## Чеки
Серверная защищённая загрузка с проверкой размера, MIME и прав доступа. При поддержке старого file_url обязательна защита от SSRF, лимиты скачивания и проверка каждого редиректа; внутренние адреса запрещены. Срок хранения согласовать.

## Вывод
Тело: amount_usdt, network=TRON, asset=USDT, wallet. Резерв из суммы к выплате. Ручной перевод с проверкой адреса, сети и транзакции. Уникальный tx hash, повторное завершение запрещено; отказ освобождает резерв вывода. Проверка формата адреса сама по себе не подтверждает его валидность или принадлежность.

## Ошибки
400 — запрос; 401 — ключ; 403 — права; 404 — объект не найден; 409 — конфликт; 422 — сумма; 429 — частота; 503 — временная недоступность. При нехватке депозита или отсутствии реквизитов не создавать частичную заявку.

## До запуска
Требуются общая БД, авторизация и роли, реальные endpoints, ключи, хранение чеков, подтверждение пополнений TRC20, журнал проводок и аудита, проверка параллельных запросов и восстановление резервной копии. Не использовать localStorage для реального финансового учёта.
